# /commit — 커밋 메시지 제안 및 커밋

## 역할
변경사항을 확인하고 Conventional Commits 형식의 커밋 메시지를 제안한다.
사용자 승인 없이 커밋을 실행하면 안 된다.
커밋 후 push는 별도 사용자 승인 게이트를 거쳐야 한다.

## 실행 순서

### 1. 변경사항 확인
```bash
git status
git diff --cached
git diff
```

### 2. 관심사 분리 판단
변경사항이 여러 관심사(기능 추가 + 버그 수정, 도메인 A + 도메인 B 등)에 걸쳐 있으면
단위별로 나눠서 커밋할 것을 제안한다.

**분리 제안 예시**
```
변경사항이 두 가지 관심사를 포함합니다.
1. Task 엔티티 및 Repository 추가 (feat)
2. User 엔티티 Auditing 필드 추가 (chore)

이 두 가지를 별도 커밋으로 나누시겠습니까?
```

### 3. 커밋 메시지 작성

**형식**
```
<type>: <한글 제목 (50자 이내)>

<본문 — 왜 변경했는지, 어떤 문제를 해결했는지>
```

**type 종류**
| type | 사용 상황 |
|---|---|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 기능 변경 없는 코드 개선 |
| `chore` | 빌드, 설정, 의존성 변경 |
| `docs` | 문서 변경 |
| `test` | 테스트 추가/수정 |
| `style` | 포맷, 공백 등 스타일 변경 (기능 무관) |

**제목 규칙**
- 한글로 작성
- 50자 이내
- 마침표 없음
- 명령형 동사로 시작 (추가, 수정, 제거, 개선)

**본문 규칙**
- "무엇을" 이 아니라 "왜" 변경했는지 작성
- 2-3문장 이내

### 4. 사용자 승인 대기
제안한 커밋 메시지를 보여주고 다음 중 하나를 선택하게 한다.
- 승인: 그대로 커밋 실행
- 수정: 수정 내용 받아 반영 후 재확인
- 취소: 커밋 중단

### 5. 커밋 실행 (승인 후에만)
```bash
git add <파일 목록>
git commit -m "..."
```

### 6. push 승인 여부 확인
커밋이 성공하면 현재 브랜치와 실행할 push 명령어를 보여주고 사용자 승인 여부를 묻는다.

```bash
git branch --show-current
git push origin <현재 브랜치명>
```

**사용자 응답별 처리**
- 승인: `git push origin <현재 브랜치명>` 실행
- 수정/보류: push하지 않고 중단
- 취소: push하지 않고 중단

push 완료 후 사용자가 PR 생성을 원하면 `/pr` 절차로 이어간다.

## 주의사항
- push는 커밋 승인과 별개로 반드시 다시 승인받은 뒤 실행
- `git push --force` 또는 `--force-with-lease` 사용 절대 금지
- `git add .` 또는 `git add -A` 사용 금지 — 파일을 명시적으로 지정
- `.env`, `application-local.yml`, `application-prod.yml` 등 민감정보 파일이 staging에 포함되면 즉시 중단하고 사용자에게 경고
- main 브랜치에서 실행 중이라면 커밋 금지
